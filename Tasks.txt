1. ISOLATION TESTS, SOFT DELETE AND BACKUPS                    priority: high
================================================================================
You're working in lordmuffin/jarvis-voice. Read the repo first (README,
CLAUDE.md, server/src/jarvis_live/{db,users,oidc,api,retention}.py, the alembic
migrations, and the np-home-homelab manifests if reachable). Write a plan to
docs/plans/isolation-and-backups.md and STOP for my approval before coding.

Context you can trust, do not re-litigate: Pocket ID sign-in and per-user
sessions already exist. There is no tenant column anywhere. There is no
deleted_at anywhere. retention.py only unlinks *.pcm for sessions in status
'done' and keeps every row forever. There is no backup tooling at all.

Goal: prove users cannot see each other's data, make deletes reversible, and
make recordings recoverable after a disk loss.

Scope:
  a) Isolation. Audit every read path -- session list, session detail, audio
     bytes, transcript, copilot output, final note, search, notify -- for a
     missing user filter. Add an integration test suite with 2 users that
     asserts 404/403 (not an empty 200) on every cross-user read and write.
     Note in the plan whether a tenant layer above users is worth adding now
     or whether user scoping is sufficient; recommend one.
  b) Soft delete. Add deleted_at to sessions. Delete hides the row and keeps
     audio and transcript. Add a "Recently deleted" list plus a restore
     endpoint for one session. Surface both in web/ and android/.
  c) Retention. Extend retention.py: after a configurable window (default 30
     days) soft-deleted sessions are hard-deleted, rows and audio together.
     Keep the existing 90-day PCM purge for live sessions as its own setting.
     Allow "delete after N days" on a single session.
  d) Backups. Schedule a Postgres dump and an audio-dir backup. Document RPO
     and RTO. Write docs/runbooks/restore.md and an automated test that
     restores one specific soft-deleted session from a backup into a scratch
     namespace and asserts the audio bytes match.

Constraints: no breaking API changes without an alembic migration; a test for
every item; Gotify notification on backup failure.
DONE WHEN: plan approved, server + web + android tests green in CI, restore
runbook committed, one real restore performed and logged in the runbook.

2. ASK ACROSS MY RECORDINGS (TRANSCRIPT RAG)                   priority: high
================================================================================
You're working in lordmuffin/jarvis-voice. Read server/src/jarvis_live/vault/
index.py, copilot/, llm/client.py and api/sessions.py first. Write a plan to
docs/plans/transcript-search.md and STOP for approval.

Goal: I want to ask "what did we decide about the Spark autoscaler" and get an
answer grounded in my own past Live sessions, with citations I can click.

Scope:
  - Chunk and embed finalized transcripts. Reuse the vault index machinery if
    it fits; say so plainly if it does not and propose the smaller thing.
  - Embeddings must run on the Spark. No third-party embedding API.
  - A search endpoint: semantic + keyword hybrid, filtered to the calling user,
    returning {session_id, timestamp_range, snippet, score}.
  - An ask endpoint: retrieve, then answer via the existing LiteLLM client,
    citing session + timestamp for every claim. Refuse to answer rather than
    guess when retrieval is weak.
  - Web UI: a search box over recordings; clicking a citation opens that
    session scrolled and seeked to the cited timestamp.
  - Backfill job for existing sessions, resumable, with progress logging.
  - An eval set of 15 real questions over my own sessions with expected source
    sessions, scored in CI as a report (not a hard gate).

Constraints: retrieval respects soft delete from task 1 and never crosses
users. Index writes happen in the finalizer, not on the hot streaming path.
DONE WHEN: I can ask a question in the web dashboard and land on the exact
moment in an old recording that answers it.

4. COPILOT SUGGESTIONS -> COMMITTED ACTIONS (HITL)             priority: high
================================================================================
You're working in lordmuffin/jarvis-voice. Read server/src/jarvis_live/
copilot/{loop,schema,state}.py, finalize/, notify/ and vault/ first. Write a
plan to docs/plans/copilot-actions.md and STOP for approval.

Goal: the copilot already notices things mid-session. I want it to be able to
DO them -- with my explicit approval, never silently.

Scope:
  - Define an action schema the copilot can emit alongside its suggestions:
    create a Work Tracker task, append to a vault note, schedule a Gotify
    reminder, open a git PR comment. Reuse the existing capture API verbs where
    they already exist instead of inventing parallel ones.
  - Every action is a PROPOSAL. It lands in a review queue on the session and
    does nothing until I approve it. Approval is one tap in web and macOS.
  - Batch approve at finalize: the session note ends with a checklist of
    proposed actions; approving the list executes them in order and records
    what happened, including failures.
  - Idempotency: re-approving or a retried execution must not double-write.
  - Full audit trail: who proposed, who approved, when, what the result was.
  - An eval over recorded sessions measuring proposal precision -- how many
    proposals I would actually accept. Report it; do not gate on it.

Constraints: nothing executes without approval, no exceptions, no "safe
actions auto-run" shortcut. A failed action is reported, not retried silently.
DONE WHEN: I finish a real session, approve a proposed task, and it appears in
20 Areas/Personal/Work Tracker.md with the session linked.

     allowed set.

     mode a running session is in.

leak, say so bluntly in the report rather than quietly patching it.
DONE WHEN: the no-egress test is green in CI and the report lists every
